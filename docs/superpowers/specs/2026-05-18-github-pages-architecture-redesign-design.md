# GitHub Pages 架构白皮书站点重构设计

## 1. 背景

当前仓库已经基于 VitePress 搭建了 GitHub Pages，并完成了一轮视觉升级与双语内容扩展。但从“高级开发者阅读的技术白皮书站点”这个目标来看，现状仍存在明显短板：

1. **站点定位不够纯粹**：首页仍偏产品宣传页，系统架构、算法、性能与证据链没有形成强主线。
2. **信息架构不够学术化**：当前目录更像并列文档集合，而不是从导读到系统模型、从原理到证据、从主张到参考文献的阅读路径。
3. **图示体系不统一**：关键页面混用 Mermaid、内嵌 SVG、主题组件，视觉语义和复杂度控制不一致。
4. **深浅色主题链路不稳**：双主题切换虽然已有 `DarkModeImage` 组件，但图示、Logo、描边、Mermaid 配色和内容页插图的适配策略尚未统一。
5. **实现层仍有真实缺陷**：已定位到根路径语言跳转表达式优先级错误、首页 Hero 重复注入、主题样式中存在无效颜色表达式、导航链接与页面存在失配风险。

本次改造不追求向后兼容，而是以“长期收益、技术先进性、可维护性、GitHub Pages 稳定部署”作为第一原则，对当前文档站进行彻底重构。

## 2. 目标

### 2.1 产品目标

将当前 GitHub Pages 重构为一个面向高级开发者的 **系统架构设计 / 算法介绍 / 技术白皮书 / 性能工程 / 参考资料** 站点，使其具备以下特征：

- 一眼建立系统级理解，而不是只看到营销文案。
- 具备“技术白皮书 + 工程设计档案 + 证据型文档”的学术感。
- 在视觉表达上更接近 research lab / systems paper / developer tooling benchmark site。
- 双语内容结构一致，且不依赖读者预先熟悉代码仓库。

### 2.2 工程目标

- 保留 **VitePress + GitHub Pages** 作为部署底层。
- 将主题、图示、内容组织与站点导航全面组件化。
- 修复现有实现缺陷，确保构建、主题切换、导航和资源引用稳定。
- 建立可持续扩展的图示系统和页面模板，后续新增章节不再依赖临时拼装。

## 3. 非目标

- 不引入自定义后端、数据库或运行时服务。
- 不把文档站扩展为交互式 Web 应用。
- 不为了炫技增加与主题定位无关的复杂动画。
- 不追求保留当前页面层级或视觉细节；旧结构可被整体替换。

## 4. 现状审计与关键问题

### 4.1 信息架构问题

- 首页包含快速上手、竞品对比和技术深度链接，但仍偏“产品首页”而不是“系统入口页”。
- 白皮书、架构、算法、性能、参考资料存在，但没有通过首页和侧边栏构成强制阅读链路。
- `guide/`、`whitepaper`、`architecture/`、`algorithms/`、`performance/`、`resources/` 的组织方式仍较平铺，缺少“导读 → 核心模型 → 论证展开 → 参考支撑”的递进关系。

### 4.2 实现缺陷

- 根路径语言重定向脚本的目标语言计算存在运算符优先级问题，保存过语言偏好时可能仍错误跳转到中文。
- 自定义主题在 `Layout` 中通过 `home-hero-after` 注入 `HeroTerminal`，而首页 Markdown 又手动插入 `<HeroTerminal />`，导致首页重复渲染风险。
- 导航中存在 `Python API` 入口，但当前文档树中未看到对应源文件，存在死链风险。
- 样式表中存在 `rgba(var(--cb-bg), 0.85)` 这类对十六进制 CSS 变量无效的写法，会让导航背景表现不确定。
- 当前 `docs/.vitepress/dist/` 已构建产物在工作树中存在，不应作为设计判断依据。

### 4.3 视觉表达问题

- 当前视觉语言强调 cyberpunk 与发光效果，但对“白皮书级、系统工程级”的专业感略偏张扬。
- 表格、图示、强调块的密度和阅读节奏还不够像技术白皮书。
- 关键架构图虽有信息量，但缺少统一的图例、层次命名、视觉编码和页面内上下文解释。

### 4.4 内容深度问题

- 白皮书已有基础结构，但对系统边界、运行时剖面、失败模式、扩展协议、性能方法学和竞争方案分析仍不足。
- 参考文献页面已有初稿，但缺少与正文的映射关系，引用更多是“列出来”而不是“被站点结构利用”。
- 演进、ADR、算法页面之间的互相指向关系不够强，证据链没有闭环。

## 5. 方案比较

### 方案 A：保守修补

在现有主题和页面基础上，仅修复 bug、优化配色、补充少量内容。

**优点**
- 实施快
- 影响面小

**缺点**
- 很难达到“颠覆式重构”的目标
- 首页、导航、图示体系的根问题会保留
- 很难形成同类项目中的显著优势

### 方案 B：VitePress 保底层、站点全面重构（推荐）

继续使用 VitePress 作为渲染引擎和 GitHub Pages 产物生成器，但对其 **内容组织、主题系统、组件层、图示层和页面骨架** 进行重写。

**优点**
- 保持 GitHub Pages 部署简洁
- 能在当前仓库稳定维护阶段下提供最高性价比的先进方案
- 允许站点视觉与内容彻底重构，同时保留 Markdown + Vue 组件的高可维护性

**缺点**
- 改动面广
- 需要同时处理信息架构、内容与主题工程

### 方案 C：迁移到定制化静态站点框架

放弃 VitePress，迁移到自定义 Vite/Vue 或其他 SSG。

**优点**
- 表现力上限最高

**缺点**
- 运维面扩大
- 会削弱仓库稳定维护阶段的工程经济性
- 对当前项目目标来说属于过度工程

**结论**：采用 **方案 B**。VitePress 继续作为基础设施存在，但从设计角度不再把站点视为“默认文档站”，而是把它当作“白皮书渲染引擎”。

## 6. 目标信息架构

### 6.1 一级结构

重构后的站点以“理解系统”为主线，推荐结构如下：

1. **Overview / 导读**
   - 首页：系统总览、设计目标、能力边界、阅读入口
   - 快速导读：适合首次进入的高级开发者
2. **Architecture / 架构**
   - 系统总览
   - 运行时流水线
   - 组件与接口边界
   - 插件与扩展协议
3. **Algorithms / 算法**
   - 规则引擎
   - ML 分类
   - 语义分析
   - 融合与置信度
   - 可选 LLM 协作
4. **Performance / 性能**
   - 基准设计
   - 并发模型
   - 缓存与资源占用
   - 性能权衡与失效边界
5. **Whitepaper / 白皮书**
   - 执行摘要
   - 系统定位
   - 技术论证
   - 演进脉络
6. **References / 参考**
   - 参考文献
   - 相关开源项目研究
   - ADR 与演进思考
7. **Reference / 参考手册**
   - CLI
   - 配置
   - taxonomy
   - Python API（若不维护则删除入口）

### 6.2 导航原则

- 顶部导航只保留最强主线，不堆叠所有页面。
- 侧边栏按“阅读模型”组织，不按目录原样映射。
- 首页成为阅读入口页，避免重复营销内容。
- 中文与英文结构镜像，文案允许表达差异，但栏目必须一致。

## 7. 视觉与交互系统设计

### 7.1 风格定位

整体风格从当前较强的 cyberpunk 风格，调整为更克制的 **Research-grade / Systems-lab** 风格：

- 大面积留白或深色留黑，但减少夸张霓虹和高频发光。
- 以“结构、证据、层级、密度控制”代替装饰性冲击。
- 让首页像一份交互化技术总览，而不是产品宣传页。

### 7.2 主题系统

建立语义化设计 token，而非继续围绕单个品牌色做视觉堆叠：

- `surface/base/elevated/muted`
- `text/secondary/tertiary/inverse`
- `accent/critical/success/warning`
- `chart-1..chart-n`
- `diagram-node/diagram-edge/diagram-group/diagram-highlight`

要求：

- 浅色主题强调冷静、精密、纸面感。
- 深色主题强调实验室、终端、工程感，但必须保持正文与图示的可读性。
- 所有图示、Logo、引用卡、指标卡、代码块都通过同一套 token 驱动。

### 7.3 首页结构

首页重构为以下顺序：

1. **Research Hero**
   - 项目一句话定位
   - 三个核心命题：离线优先、规则优先、融合架构
   - 白皮书 / 架构 / 性能三入口
2. **System Snapshot**
   - 关键指标条：处理速度、启动时延、模式开关、输出格式
3. **Architecture Map**
   - 系统全景图，作为站点核心视觉锚点
4. **Evidence Grid**
   - 以证据而非口号展示：架构边界、算法理由、性能结论、隐私保障
5. **Reading Paths**
   - 为不同读者提供入口：架构读者 / 算法读者 / 性能读者 / 贡献者
6. **Comparative Framing**
   - 与同类项目和传统脚本的对照，但采用更加严谨的指标描述
7. **Citation / Further Reading**
   - 直接把文献与相关项目嵌入首页底部，形成白皮书延伸

### 7.4 交互原则

- 动效只作为状态反馈，不做持续分散注意力的表演。
- 大多数 hover 交互要轻，且在 reduced motion 下可退化。
- 目录、图示卡片、引用卡片、指标卡统一交互语言。

## 8. 图示系统设计

### 8.1 分层策略

图示分为两类：

1. **一级关键图示**
   - 首页系统图
   - 处理流水线总图
   - 多分类器融合图
   - 性能剖面图
   - 这些图用 Vue + SVG 组件实现，确保可控、可主题化、可精修排版

2. **二级辅助图示**
   - 局部流程图
   - 时序图
   - ADR 结构图
   - 这些图继续使用 Mermaid，但需要统一主题变量与容器样式

### 8.2 图示规范

所有关键图示遵守统一规范：

- 固定图例位置与命名习惯
- 节点采用分层容器，体现 entry / orchestration / processing / intelligence / output
- 边线宽度、圆角、阴影、高亮色统一
- 深浅色模式下均保持 4.5:1 以上关键文本对比
- 不依赖纯颜色区分类别，辅以图标、标签和层级布局

### 8.3 深浅色图示适配

- 不再依赖“浅色一张图、深色一张图”的零散人工方式作为主路径。
- 首选基于 CSS 变量的 SVG 组件化图示。
- 保留 `DarkModeImage` 作为兼容路径，但将其升级为统一图像包装器，支持：
  - `picture` / `source` 方案
  - 深浅色 caption 样式
  - 高 DPI / loading / decoding 策略
- 对必须使用静态图的场景，成对提供 `*-light.svg` 与 `*-dark.svg` 资源。

## 9. 内容重构设计

### 9.1 白皮书页

白皮书将从“项目介绍文档”升级为“技术论证文档”，新增或强化以下章节：

- 问题空间与设计约束
- 系统边界与运行时模型
- 分类器协作机制与权重选择理由
- 置信度校准的工程意义
- 性能方法学与 benchmark 假设
- 失效模式与回退策略
- 可扩展性与未来演进边界
- 竞品与替代路线分析
- 参考文献与正文引用映射

### 9.2 架构页

架构章节从“描述组件”升级为“解释系统如何被组织”：

- 总览页先解释层次模型，再链接到具体页面
- `pipeline` 聚焦数据流与阶段职责
- `container` 聚焦依赖注入、组合根与可测试性
- `protocols` 聚焦接口边界与扩展契约
- 必要时新增一页 `system-overview` 或 `runtime-model`

### 9.3 算法页

每页都需要回答三件事：

1. 该模块解决什么问题
2. 为什么采用当前算法/策略而不是替代方案
3. 在整个系统中的输入输出位置是什么

特别是融合页和 LLM 页，要减少“能力罗列”，强化“工程权衡”。

### 9.4 性能页

性能章节应从概念陈述升级为证据页：

- 明确 benchmark 场景、输入规模、硬件假设
- 区分冷启动、热启动、规则命中、ML 参与、LLM 参与等路径
- 对并发模型和缓存策略给出局限与收益范围

### 9.5 参考与学术模块

新增更强的学术表达：

- 正文中的关键论断使用引用标记映射到参考页
- `related-projects` 不再只是列表，而是从架构模型、部署模型、离线能力、扩展性几个维度做研究式对照
- `evolution` 页强调架构演进逻辑，而不是流水账式历史

## 10. 站点工程设计

### 10.1 配置层

重构 `docs/.vitepress/config.ts`：

- 抽离双语公共导航与侧边栏生成逻辑
- 收敛 head/meta 配置
- 修复根路径语言跳转逻辑
- 明确首页、白皮书和参考页的社交元信息

### 10.2 主题层

重构 `docs/.vitepress/theme/`：

- 将主题样式拆分为 token、layout、components、docs-content 等更清晰的层次
- 保留 `index.ts` 作为组件注册入口，但避免首页重复注入
- 为关键首页与图示建立新的 Vue 组件

建议新增或重构组件：

- `ResearchHero.vue`
- `SystemMap.vue`
- `EvidenceStrip.vue`
- `ReadingPathGrid.vue`
- `BenchmarkMatrix.vue`
- `CitationCluster.vue`
- `ThemedFigure.vue`（统一替代现有 `DarkModeImage` 语义）

### 10.3 内容层

- 重写首页与白皮书页骨架
- 补齐或删除失配链接（如 Python API）
- 统一中英文页面 Frontmatter 与结构
- 将关键图示从文档内零散代码块迁移到复用组件

## 11. 兼容性与风险控制

### 11.1 GitHub Pages 兼容性

- 保持纯静态输出
- 不依赖运行时 API
- 不引入需要 SSR 或 Node 服务器参与的功能

### 11.2 风险

1. **改动面大**：主题、内容、导航会同时变化，需要分阶段落地。
2. **双语同步成本高**：中文和英文必须结构一致，否则会快速漂移。
3. **Mermaid 可控性有限**：关键图示若仍留在 Mermaid 中，难以达到商业级插图质感。

### 11.3 风险应对

- 将关键图示组件化，Mermaid 只留辅助用途
- 以统一内容模板驱动中英文章节
- 先修 bug 和 IA 主线，再做精修内容与视觉强化

## 12. 实施阶段

建议按以下阶段执行：

### 阶段 1：结构与缺陷修复

- 修复根路径语言跳转
- 修复重复 Hero 注入
- 修复主题样式问题
- 校验并清理失配链接
- 重构顶部导航和侧边栏主线

### 阶段 2：主题与首页重建

- 引入新的 token 系统
- 重写首页布局与关键组件
- 建立主题感知图示层

### 阶段 3：核心内容升级

- 重写白皮书
- 重构架构与算法关键页
- 补强性能、参考文献、相关项目研究

### 阶段 4：收口与验证

- 全量构建与渲染检查
- 深浅色模式巡检
- 链接、目录、图示、双语结构一致性检查

## 13. 验收标准

当以下条件全部满足时，本次重构视为完成：

1. 首页能清晰传达系统模型、技术路线和阅读入口。
2. 顶部导航和侧边栏体现“导读 → 架构 → 算法 → 性能 → 白皮书 → 参考”的主逻辑。
3. 深浅色模式下所有关键 SVG / 图示 / Logo / Mermaid 图都可读且风格一致。
4. 关键页面具有白皮书级内容深度，而不是单纯说明功能。
5. 死链、重复注入、主题样式和资源适配问题全部修复。
6. GitHub Pages 构建产物稳定，站点能在当前 workflow 下正常部署。

## 14. 设计结论

本次重构不应被视为“继续装修文档主题”，而应被视为将现有 GitHub Pages 从 **默认文档站** 升级为 **架构与算法白皮书站点**。  
核心策略是：**保留 VitePress 作为稳固基础设施，重写站点表达层、图示层和内容结构层，以更小的长期维护成本换取显著更高的专业表达上限。**
