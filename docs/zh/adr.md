# 架构决策记录 (ADR)

本文档记录 Bookmarks Cleaner 在设计与实现过程中的关键架构决策及其技术权衡。每条决策遵循 ADR 标准格式：背景、决策、后果。

## ADR-001: Pipeline 架构而非 DAG

**状态**: 已采纳 | **日期**: 2025-03

### 背景

书签处理本质上是一个线性变换序列：加载 → 去重 → 分类 → 组织 → 导出。但在设计初期，团队考虑过更通用的 DAG（有向无环图）执行引擎，以支持未来可能的非线性处理（如分支、条件跳转）。

### 决策

采用**五阶段线性 Pipeline**，而非 DAG 引擎。

### 理由

1. **认知复杂度**：DAG 配置对 CLI 用户来说过于复杂；线性 Pipeline 的语义一目了然
2. **性能**：线性执行避免了 DAG 调度器的拓扑排序开销和动态调度开销
3. **可测试性**：线性管道的输入/输出契约清晰，每个阶段可独立单元测试
4. **YAGNI**：当前及可预见未来的需求均为线性处理，DAG 是过度工程

### 后果

- **正**：代码量减少约 40%，维护成本显著降低
- **负**：若未来需要条件分支（如"仅当置信度低时启用 LLM"），需在 Pipeline 内部实现，而非通过拓扑调度

## ADR-002: ThreadPool 而非 Asyncio

**状态**: 已采纳 | **日期**: 2025-03

### 背景

并发处理是性能优化的关键。Python 生态提供了 `asyncio`（协程）和 `ThreadPoolExecutor`（多线程）两种主要并发模型。

### 决策

采用 `ThreadPoolExecutor` 实现并发分类。

### 理由

1. **库兼容性**：scikit-learn、sentence-transformers 等核心依赖未原生支持 async/await
2. **CPU 密集性**：书签分类以文本特征提取和模型推理为主，属于 CPU 密集型任务，GIL 并非瓶颈
3. **调试成本**：线程异常栈直接明了；asyncio 的调用链追踪在复杂场景下困难
4. **API 简洁性**：`concurrent.futures` 接口比 asyncio 更易上手

### 后果

- **正**：与现有 ML 生态无缝集成，无需封装异步适配层
- **负**：在 I/O 密集型场景（如大规模 LLM API 调用）下，协程模型的资源效率更高

## ADR-003: Protocol 接口而非抽象基类

**状态**: 已采纳 | **日期**: 2025-04

### 背景

Python 提供了两种定义接口的方式：`abc.ABC`（抽象基类）和 `typing.Protocol`（结构化子类型）。项目需要为分类器、Pipeline、协调器等定义契约。

### 决策

采用 `typing.Protocol` 定义所有核心接口。

### 理由

1. **非侵入性**：Protocol 不要求实现类显式继承，避免了继承耦合
2. **鸭子类型**：任何实现了协议方法的类自动满足接口，无需修改现有代码
3. **类型检查器支持**：mypy 对 Protocol 的支持成熟，可进行静态类型检查
4. **Pythonic**：符合 "如果它走起来像鸭子..." 的 Python 哲学

### 后果

- **正**：第三方扩展无需继承项目内部类，降低集成门槛
- **负**：运行时检查需额外实现（使用 `isinstance` + Protocol 在 Python 3.8+ 可用，但行为略有不同）

## ADR-004: 加权投票融合而非 Stacking

**状态**: 已采纳 | **日期**: 2025-04

### 背景

多分类器融合的常见方法包括：
- **Bagging**：同质分类器并行，多数投票
- **Boosting**：串行训练，关注错误样本
- **Stacking**：元学习器融合各分类器输出
- **加权投票**：简单线性组合

### 决策

采用**加权投票**作为默认融合策略，Stacking 作为可插拔扩展。

### 理由

1. **异构输出空间**：规则引擎输出离散类别（置信度=1.0），而 ML/LLM 输出概率分布。Stacking 的元学习器难以处理这种异构性
2. **冷启动**：加权投票无需训练数据；Stacking 需要额外的 hold-out 集训练元模型
3. **可解释性**：加权投票的决策过程完全透明，每个分类器的贡献可精确计算
4. **计算开销**：加权投票的时间复杂度为 O(n)，Stacking 为 O(n) + 元推理开销

### 后果

- **正**：用户零配置即可获得良好融合效果
- **负**：在分类器数量增多（>10）且存在复杂交互时，Stacking 可能捕捉非线性组合模式

## ADR-005: dataclass DI 容器而非框架

**状态**: 已采纳 | **日期**: 2025-04

### 背景

组件管理考虑过引入依赖注入框架（如 `dependency-injector`、`inject`）或手动实现容器。

### 决策

使用标准库 `dataclasses.dataclass` 实现轻量级 DI 容器 `ProcessorContainer`。

### 理由

1. **零依赖**：不引入第三方 DI 框架，保持项目轻量
2. **延迟创建**：通过 property 实现组件的惰性初始化
3. **可注入性**：所有组件字段以 `_` 开头，支持测试时直接注入 mock
4. **类型安全**：dataclass 的字段声明自带类型注解

```python
@dataclass
class ProcessorContainer:
    config: Dict[str, Any]
    _coordinator: Optional["ICoordinator"] = field(default=None, repr=False)
```

### 后果

- **正**：代码自包含，无外部依赖风险
- **负**：生命周期管理（如单例/作用域）需手动实现，不如专业框架完善

## ADR-006: 门面模式重构上帝类

**状态**: 已采纳 | **日期**: 2025-04

### 背景

原始实现中 `BookmarkProcessor` 是一个 1,148 行的"上帝类"，承担了加载、去重、分类、组织、导出、LLM 集成、健康检查等全部职责。

### 决策

将 `BookmarkProcessor` 重构为**门面类（~350 行）**，核心逻辑委托给 `BookmarkProcessorCoordinator` 和五个 Pipeline。

### 理由

1. **单一职责**：每个类只做一件事，符合 SOLID 原则
2. **可测试性**：门面类可通过注入 mock Container 进行单元测试，无需构造完整依赖树
3. **可替换性**：任意 Pipeline 可被自定义实现替换，不影响其他阶段
4. **认知负荷**：开发者只需理解当前修改的 Pipeline，无需通读 1,148 行代码

### 后果

- **正**：代码可维护性显著提升，新功能开发周期缩短
- **负**：增加了类数量和文件数量，导航成本略有上升（被 IDE 的跳转功能抵消）

## ADR-007: 置信度校准默认启用

**状态**: 已采纳 | **日期**: 2025-05

### 背景

ML 模型和语义分析器输出的原始置信度往往存在系统性偏差（如神经网络倾向于 over-confidence）。

### 决策

默认启用 Platt Scaling 校准，用户可通过配置切换至 Isotonic Regression 或禁用。

### 理由

1. **准确性**：校准后的置信度更接近真实概率，提升融合引擎的决策质量
2. **低开销**：Platt Scaling 仅需拟合两个参数（a, b），计算成本可忽略
3. **可配置**：保留灵活性，允许高级用户选择其他校准策略

### 后果

- **正**：融合后的分类准确率提升约 3~5%
- **负**：需要收集一定量的反馈数据才能拟合最优校准参数（冷启动时退化为恒等映射）
